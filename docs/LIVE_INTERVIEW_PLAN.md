# 대면 면접 녹음 → AI 평가 리포트 (설계)

> 사람이 진행하는 **대면 면접**을 녹음·전사해 AI 역량 평가 리포트를 생성한다. **업로드 + 준실시간** 투트랙이며, 두 모드의 결과 리포트는 **동일**하다.
> **상태: 설계 확정, 미착수.** 착수 전 선행으로 Gemini 화자분리/역할배정 실측이 필요하다 (Phase 0).
> 기존 AI 채팅 면접(`/interview/[token]`)과는 **별개 기능** — 그건 AI가 직접 진행, 이건 사람이 진행하고 AI가 보조·평가한다.

---

## 1. 목표 · 타겟

- **타겟**: 중소기업. 전문 면접관도, 정해진 면접 프로세스도 없는 곳.
- **가치**: "기록을 남겨주는 것"이 아니라 **AI가 대면 면접 평가서를 대신 써주는 것**(AI 면접과 같은 종류의 노동 대체). 그래서 가격 인식도 AI 면접급(₩3,000대)으로 잡을 수 있다.
- "로깅 도구"로 포지셔닝하면 어떤 가격도 "불필요"하게 느껴진다 → **의사결정 도구**로 포지셔닝한다.

## 2. 스코프 — 불변식 "1세션 = 1지원자"

| 유형 | 지원자 수 | 지원 |
|---|---|---|
| 1:1 | 1명 | ✅ |
| 다:1 (패널) | 1명 | ✅ |
| 다:다 (집단/토론) | 여러 명 | ❌ 스코프 아웃 |

- 지원자가 1명이면 화자분리가 **"지원자 vs 면접관" 이진 문제**라 견고하다.
- 여러 명이면 후보자 상호 구분 + "화자N이 누구인지" 매핑이 필요한데 오디오만으로는 불가(수동 라벨링 + 오류 전파). 게다가 집단면접은 평가 축(상호작용·리더십)이 달라 **1인 역량 리포트 모델이 맞지 않는다.**
- Intervia 데이터 모델(`candidates`·세션이 1인 단위)과도 부합한다.
- **패널 표시 방식**: recorder 1대 + 사후 리포트(각자 자기 기기로 열람). 라이브가 필요하면 **"리드 서기 1명"만 화면**을 보고 나머지는 면접에 집중. 다기기 동기화는 오버엔지니어링(보류).

## 3. 두 모드 (결과 동일)

- **업로드 모드**: 종료 후 오디오 파일 1개 → 배치 전사.
- **준실시간 모드**: 마이크 청크(~10초) → 즉시 전사 + 라이브 추천질문(서기 화면). 종료 시 동일 평가.
- **공유 코어**: `트랜스크립트 텍스트 저장 → (종료) 역할 배정 패스 → 평가 → 리포트`. 모드는 **입력 경로만** 다르다 → 두 개가 아니라 1.5개를 만드는 셈.
- 준실시간 추천질문 = **얇은 폴링 레이어**(쌓이는 트랜스크립트를 30초마다 롤링 요약 → LLM 1회 → 서기 화면). 끄면 그대로 업로드 모드와 같다.
- 지연: 청크 전사 + 추천 LLM이라 추천이 관련 답변 뒤 **약 15~40초** 후 표시("즉시" 아님).
- 인프라: 클라이언트가 청크를 끊어 보내고 서버는 **짧은 POST(청크) + 짧은 폴(추천)** 만 처리 → 롱-라이브 소켓 불필요, **Vercel 서버리스 친화**.

## 4. 화자분리 전략 (핵심 단순화)

- **음향 다이어리제이션 = 턴 경계(말하는 사람이 바뀌는 지점)만** 담당. 라이브 화면은 러프한 화자1/2 라벨로 충분.
- **역할(지원자/면접관) = 종료 시 Gemini가 전체 트랜스크립트를 내용으로 배정** (질문하는 쪽=면접관, 경험을 서술하는 쪽=지원자). LLM 추론이라 "지원자 역질문" 같은 예외도 처리. → 음향 라벨의 **한 시간 일관성 의존도가 사라진다**(가장 무서웠던 리스크 무력화).
- **한계**: 진짜 동시 발화로 단어가 한 덩어리로 뭉친 구간은 내용 검토로도 못 가른다 → "저신뢰" 표시. 면접은 턴 기반이라 드문 엣지케이스.
- **안전망**: 리포트에서 사람이 화자 라벨을 확정·수정.

## 5. 리포트 구조

위 → 아래: **① 결정 요약**(등급·점수·핵심 강점/확인필요) → **② 역량 평가**(영역별 + **근거 발언 → 전사 점프**) → **③ 확인 필요(판단 리스크)** [다음 라운드가 있으면 + 추천 질문 인계] → **④ 화자분리 전사**(저신뢰 구간 표시) → **⑤ "AI 생성 · 최종 판단은 면접관" + 확정 버튼**.

- 평가 로직: 기존 `lib/prompts.ts` `buildSummaryPrompt` 재사용·확장.
- **부정행위(`ai_authorship`/외부 LLM 보조) 신호는 제거** — 대면 라이브는 사람 앞 즉답이라 무의미.
- **근거 발언 → 전사 점프**가 "기록"과 "의사결정 도구"를 가르는 핵심 기능(신뢰·설명가능성).
- 기존 대면 **결과 입력** 단계(`lib/candidate-state.ts` `r1_result_due`/`r2_result_due`)를 이 리포트가 대체 — AI 초안 → 사람 확정.
- **추천 질문**: 준실시간은 면접 중 라이브(서기). post-hoc 리포트의 "추천 질문"은 **다음 라운드가 있을 때만** 노출(질문지 생성에 인계). 마지막 면접이면 "확인 필요(판단 리스크)"로만 남긴다.

## 6. 원가 · 과금 (환율 1550 가정)

- post-hoc ≈ **₩200~350/시간**, 준실시간(Gemini 오디오 마이크로배치) ≈ **₩300~450/시간**.
- 전용 스트리밍 STT를 쓰면 ₩1,000~1,500(화상 실시간 모드용, 보류).
- **비용 동인은 STT 엔진 선택이지 "실시간성"이 아니다.** 코파일럿 LLM은 +₩100 남짓.
- 과금: **후차감 신규 카테고리**(`lib/tokens.ts` `chargeFeature`). 멱등 유지. 단가/단위는 L-3.

## 7. 컴플라이언스

- **통신비밀보호법**: 면접관이 대화 당사자 → 당사자 녹음은 합법(고지 없이도). 걸림돌 아님.
- **개인정보보호법**: 음성·전사 = 개인정보. **민감정보 아님**(성문 식별을 안 하므로) — 화자 식별용 성문 DB 금지. 수집·이용 동의 필요 → `lib/consent-template.ts` 항목 추가. 파기: 오디오는 즉시/종료 시 폐기, 텍스트는 폐기 cron.
- **AI 기본법·채용절차법**: AI 평가 고지 + 거부권/인간 검토 → 기존 §37의2 틀 확장.
- **국외이전(§28의8)**: Gemini = Vertex AI 서울 → 회피. (전용 STT 도입 시 asia-northeast3 여부 필수 확인.)
- **위탁**: 고객사 = 처리자, Intervia = 수탁자(기존 구조 동일).
- 현재 동의 v1.7.0도 법무 미확인 상태 → 이 항목과 묶어 법무 사인오프.

## 8. 열린 결정

- **L-1 화자분리 품질 vs 프라이버시**: (a) *no-file* — 오디오 청크 즉시 폐기 + 라이브 텍스트 스티칭(라벨 품질 약간↓, "녹음 안 남김" 순수) / (b) *keep-until-end* — 오디오를 면접 끝까지 보관 후 한 번에 깨끗이 재diarize → 폐기(품질↑, 오디오 잠깐 존재).
  - **결정(2026-06-17, 업로드 모드 한정)**: **(b) keep-until-end 채택** — 업로드 모드를 백그라운드 큐로 전환하면서, 오디오를 워커가 전사할 때까지만 임시 저장(Blob/로컬)하고 **전사 직후 즉시 폐기**한다(`processRecordedInterview` 성공·영구실패·stuck-fail·파기 cron 4중 폐기 경로). "전사 후 미보관" 원칙은 유지되며, 임시 보관 윈도우만 요청 처리 시간 → 워커 처리 시간으로 늘어난다. 동의 문구("전사 후 보관하지 않습니다")는 여전히 정확. 준실시간 모드는 기존대로 청크 즉시 폐기(no-file).
  - **결정(2026-07-05, 준실시간 모드도 A안 = keep-until-end 전환)**: 라이브 화면 Web Speech 는 말이 많거나 화자가 여럿이면 인식이 뭉개지고, 그 저품질 텍스트로 평가하면 리포트가 흔들린다. → **라이브 화면(Web Speech)은 그대로 두되, 오디오를 MediaRecorder(Opus 24kbps mono)로 병행 녹음**해 종료 시 업로드 파이프라인에 태워 **Gemini 로 재전사한 결과를 최종 리포트 근거로** 삼는다. "면접 중 UX 동일, 최종 품질 = 업로드 모드"가 목표. 오디오는 브라우저 밖으로 나가지만 전사 직후 폐기(업로드 모드와 **바이트 단위로 동일한** 4중 경로 — 워커 ①전사→오디오 즉시 `deleteFile`→②평가 순서라 평가 전에 사라짐). **오디오는 IndexedDB 에 청크로 적재**해 업로드 도중 새로고침해도 유실 없이 다음 로드에서 자동 재개(패널 마운트 시 복구). 마이크 캡처 실패(권한 거부)·오디오 empty 면 기존 텍스트 초안으로 폴백(action=finish). 재전사 실패 시에도 초안 세그먼트는 보존돼 '평가 다시 시도'로 폴백 가능. 구현: `live-recording-store.ts`(IndexedDB+업로드), `recorded-interview-live.tsx`(병행녹음), 업로드 라우트 `recordedInterviewId` attach 분기, 워커 전사 게이트 `!hasSegments`→`audioBlobKey 있으면 재전사(초안 교체)`, `finalize` 역할배정 조건 `mode!=='live'`→`역할 미배정(role=null)`.
  - **문구/법무(2026-07-05 확인)**: A안은 업로드 모드가 이미 운영 중인 "오디오→서버→전사→즉시 폐기" 흐름을 라이브에도 그대로 적용한 것뿐 — **새 법무 이슈 없음**. 처리방침·응시자 안내문·동의 템플릿엔 애초에 녹음/오디오/전사 언급이 없어(어느 모드도), A안이 깨뜨릴 문구가 없다. 유일하게 틀렸던 라이브 UI "음성은 기기 밖으로 저장되지 않습니다"만 "전사 위해 임시저장 후 폐기"로 갱신 완료. 공용 동의 체크박스 "녹음 파일은 전사 후 보관하지 않습니다"는 원래 정확 = 두 모드 공통 커버. (처리방침에 대면 녹음 처리가 명시 안 된 건 업로드 모드부터의 기존 상태지 A안 발생 이슈 아님.)
- **L-2 STT 엔진**: Gemini 오디오 마이크로배치(확정 방향, 저비용·서울 리전) / 전용 스트리밍 STT는 화상 실시간 모드용으로 보류.
- **L-3 과금 단위·단가**: 시간당 vs 면접 건당.
- **L-4 화상 실시간 라이브 코파일럿**(원래 스크린샷 그대로): 별도·후순위. 화상 1:1 고객이 생기면 같은 전사·평가 자산으로 추가.
